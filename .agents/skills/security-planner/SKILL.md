# 資安規劃師

把可追溯的適用要求交給設計、開發及 QA，持續維護證據與表單。單獨使用或由 MingMing 呼叫皆可。讀本次專案指引與工作流選擇，純討論不自行進入實作。

## 啟動與輸入

政府標案已確認為「是」就啟動，防護等級未知也能整理來源及待確認事項；非政府案件只有使用者要求時才套用相關規劃。既有答案直接沿用，不逐節點重問。

先取得專案範圍、系統邊界、系統防護需求等級及依據、政策採納選擇，以及已提供的 RFP、契約、查核表。按需確認核心系統、客製化、委託金額、個資、部署環境與第三方檢測責任。先查文件，重要資訊仍缺才問。機關 A～E 與系統高／中／普分開記錄。

## 工作順序

1. 讀 [來源與適用性](references/sources.md)，查核本案適用法規及官方版本，保存來源、定位、查核日期。不要以搜尋摘要或已勾選的示範表格作為證據。
2. 讀 [資料與證據契約](references/data-contract.md)。以 `assets/baseline.json` 與本案文件建立 `security-plan.json`；工具產生的是待確認草稿。內建 27 個防護基準控制項採行別摘要，逐項仍須核對原表各款。普／中無要求的特定列不表示其他法規或契約也無要求。
3. 依 [操作指南](references/operations.md)產生清單。合併法規、契約、機關要求、廠商程序及自願採納項目，保留每個來源。把複合條文的每一款落實到措施與驗證步驟；同一實作可對應多份表單。
4. 在總表填入適用性、責任、設計措施、驗收方式、Node 與表單對照。MingMing 的主線把 `feature.security` 連到本表；Node 的執行狀態仍以原 state.json 為準。規劃中的事項不勾符合。
5. architect／developer 實作，QA 執行授權範圍內的檢查，reviewer 核對適用性、完整性及證據語意。依實際證據回填；同一 agent 切角色如實標 self-review，不宣稱獨立或第三方檢測。
6. 依 [表單處理](references/forms.md)保存原檔、建立欄位對照、填寫副本並檢查版面。對尚未實作的欄位填規劃措施或留待補，不虛構組織制度、訓練、證照、簽章或機關核定。
7. 變更規格、程式、設定、等級或來源版本時，重新評估受影響項目；舊證據保留，hash 不符不能放行。交付總表、表單副本、證據索引、待補事項及正式人員／第三方待辦。

## 邊界

- 法令、契約與機關要求不能因使用者不採額外建議而省略；範本、年度稽核計畫不自動成為每案義務。
- 工具只檢查結構、覆蓋及所列檔案的 hash，不證明測試有效或法律適用正確。先做來源／契約語意覆核，再開啟規劃或交付門檻。
- 機關／第三方執行或簽署的項目保留實際責任，AI 只協助準備；不得以程式單測代替安全檢測證明。
- 本 Skill 不額外授權發送文件、使用付費檢測、掃描正式系統、上傳機敏資料或刪除資料。

工具使用 Node.js 22+，無第三方依賴；命令與限制見操作指南。Word／Excel／PDF 依實際可用的文件工具處理，無法可靠解析或保留格式時標示阻礙，提供欄位回填草稿，不聲稱已完成原檔填寫。
